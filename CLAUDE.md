# Ghost Path: working notes for Claude

> **In a new container, run `scripts/setup-container.sh` first** (installs JDK 25, points Gradle at it, installs the Maven Central mirror init script; safe to run twice). Then `./gradlew build`.

Fabric mod for **Minecraft Java 26.2** that shows where TNT and projectiles will go. Design and verified findings: `docs/DESIGN.md`. Read it first.

## Ground rules
- **Target:** Minecraft Java **26.2**, Fabric. Don't assume anything from 1.21.x still holds. 26.x is unobfuscated: no Yarn, use Mojang names exactly as `genSources` shows them.
- **Java 25.** `scripts/setup-container.sh` installs `openjdk-25-jdk-headless` and points Gradle's daemon at it in the user file `~/.gradle/gradle.properties` (`org.gradle.java.home=...`), not in the repo.
- **Never assume vanilla code exists or behaves a certain way.** Find the real method in the 26.2 sources with grep before writing a mixin or relying on a vanilla method. Quote class, method and line in a comment above each mixin. If the design doesn't match the source, stop and tell the user instead of working around it.
- **Source of truth:** only the decompiled source from `./gradlew genSources` on the official 26.2 jar. No third-party repos of Minecraft code. Keep generated sources outside git (they live in `.gradle/loom-cache`, which is ignored; unzip copies go in the scratchpad).
- **Check against the source three ways:** (1) read it; (2) let the build check it: a mixin whose target doesn't exist must fail the build or start-up, never use `require = 0`; (3) run the real game: behavior is confirmed with game tests on a headless 26.2 server, and when the source and a test disagree, the test wins and the finding goes in `docs/DESIGN.md`.
- If `genSources` fails, stop and report the exact error.
- Look up versions (meta.fabricmc.net, maven.fabricmc.net, maven.nucleoid.xyz), don't guess.
- Save tokens: grep for specific methods, run builds from the command line and read only failing output.
- When reporting problems, list them briefly first; give fixes and a plan only when asked.

## Commands
- Build: `./gradlew build`
- Game tests (headless 26.2 server): `./gradlew runGameTest` (exit code 1 on any failed required test; results in the log, `build/run/gameTest/`)
- Decompile: `./gradlew genSources`; jars end up in `.gradle/loom-cache/minecraftMaven/net/minecraft/minecraft-{common,clientOnly}-*/26.2/*-sources.jar`
- Run client: `./gradlew runClient`
- Client game test (real client, virtual display, llvmpipe; not part of `build`): `xvfb-run -a -s "-screen 0 1280x720x24" ./gradlew runClientGameTest` (screenshots in `build/run/clientGameTest/screenshots/`). **Take them with `ClientShots.capture`** (vanilla's capture of the main render target: gizmos, HUD and panels are in it). Fabric's `context.takeScreenshot` re-renders a frame without gizmos (DESIGN "Gizmo visibility"). Real input is available (`context.getInput()`: keys, mouse, scroll). ~1 minute.

## Sandbox quirks (this cloud environment)
- `repo.maven.apache.org` returns HTTP 429 from the shared IP. `~/.gradle/init.d/central-mirror.gradle` (written by `scripts/setup-container.sh`, user level, not in the repo) rewrites it to `repo1.maven.org`; `settings.gradle` also lists repo1. If a build still hits a 429, just rerun: Gradle caches what it got.
- Game tests: the framework puts a barrier shell around each test structure (use `TestSupport.removeBarriers` for machines larger than 8x8x8); tests tick at full speed while chunk loading takes real time, so tests that wait for chunks need a large `maxTicks`.
- Seen once in five full runs: a delayed test callback lost in the harness map (`GameTestInfo.tickInternal` iterates it while callbacks add entries), `ghostcheck_shift` never finishes and its ghost keeps the autosave guard, so the tests after it fail with "saves are already held". A rerun passes; `TestSupport.later/once` only guard against a callback running twice.
- **Waits on asynchronous work (chunks, entities, IO) use real time, never a tick count**: `maxTicks = TestSupport.ASYNC_MAX_TICKS` and `TestSupport.overRealTime(helper)` (180 s). Under load 12000 ticks went by in one second. Never schedule many harness callbacks at once (a loop of `runAfterDelay`): use `TestSupport.eachTick` (the harness map can lose a callback). Never leave a `PathSettings` value changed after a test (pass a limit to `MachineRecorder.start` instead). Wait for **every** forced chunk (`CauseTrackingTest.forceChunks` / `TestSupport.forceAround` note them; the shared `when*Ticking` helpers check them), not a few positions.
- Flakes: `scripts/repeat-gametest.sh [--stress[=N]] <runs> [selector]` (busy loops during each run; logs of failed runs in `build/repeat/<tag>-<stamp>-<i>.log`). `runGameTest` starts from a fresh world (it deletes `build/run/gameTest/world`). Don't compile (`./gradlew ...`) while a repeat run is going: a starting run then misses classes.
- Game tests tick as fast as they can; a real game ticks at 20 per second. Anything that waits for something asynchronous (chunk loads) **per tick** can pass headless and never finish for real: that hid the live rerun's chunk wait for two steps (fixed, DESIGN "Live rerun: the ghost chunks' wait"). Check such code in the client test.
- Ghost tests that create a ghost each need **their own environment file** (`src/gametest/resources/data/ghostpath-gametest/test_environment/`): tests of one environment run in one batch, concurrently, and two ghosts fight for the autosave guard ("saves are already held").
- Projectile tests: force-load the chunks around the structure (`TestSupport.forceAround`), or an arrow that leaves the structure's chunk stops being ticked and holds the recording to the limit (the structure's chunk offset differs every run).
- Client tests run in lockstep with the server (the server thread parks at a phaser between ticks; thread dumps show that, it is not a stall). Client options (F3 debug entries) outlive the world in one JVM: undo them at the end of a test.
- A game-test mod only exists if `fabricApi.configureTests { createSourceSet = true }` is set (already is). Never trust "N tests passed" without checking that our test's name appears in the log.

## Environment
`fabric.mod.json` says `"environment": "*"` **only so the game tests load** on a dedicated headless server. The mod is meant to be used client-side in singleplayer (built-in server). Don't read `*` as a promise of dedicated-server or multiplayer support.

## Layout
- `src/main` common code, `src/client` client-only code (`GhostPathClient`, `PathRenderer`, `Tails`, client mixin), `src/gametest` game tests (mod id `ghostpath-gametest`, entrypoint keys `fabric-gametest` and `fabric-client-gametest`).

### Step 6: what to look at in the game (the cloud cannot show a real GPU, a real mouse or real feel)
Same machine as above, `/path machine x y z`. Key **V** (controls, "Ghost Path", "Inspect"; rebindable).
1. **Hover a dot or a path:** point the crosshair at a dot (no key): the entity's bounding box and a panel next to the crosshair. Is the panel readable at your GUI scale and window size? Does the pick feel right (tolerance `0.1 + 0.01 x distance` blocks; nearest to the camera wins) or too fussy / too loose? Does it flicker between two paths close together?
2. **Through blocks:** a path behind a wall is not hovered; hold V and it is.
3. **Pin:** hold V, left click on a dot (message above the hotbar, white box + `pin t+N`, panel top right); click it again: unpin. Nothing is broken or attacked while V is held. Many pins: columns to the left.
4. **Pin across a rerun:** pin a dot, then change the machine so the path changes (a piston, a block in the path): after the rerun the pin is still on its tick; if the new path ends before that tick it says so in the panel and comes back when you undo the change.
